# 界面语言与本地化（i18n）

> 适用版本：Narvive 1.0.0+
> 本文说明三语（简体中文 / 繁體中文 / English）界面的实现机制、资源组织方式，以及**新增一门语言的操作步骤**。

---

## 1. 支持的语言

| 语言 | 资源目录 | BCP-47 标签 | 说明 |
| --- | --- | --- | --- |
| 简体中文 | `res/values/` | `zh-Hans` | **默认语言**（基准资源，新增文案先写这里） |
| 繁體中文 | `res/values-b+zh+Hant/` | `zh-Hant` | 单一繁体，采台湾/通用用词 |
| English | `res/values-en/` | `en` | |

中国传统语标签在资源目录名里写作 `b+zh+Hant`（BCP-47 限定符），而不是 `values-zh-rTW`——前者能同时被 `zh-Hant`、`zh-TW`、`zh-HK` 匹配，覆盖更广。

用户在**设置 → 语言**中切换（独立页面，三项：简体中文 / 繁體中文 / English；每个语言一行，当前语言带勾选标记）。切换即时生效，无需重启。

## 2. 切换机制

使用 **AndroidX 官方 per-app language**（`AppCompatDelegate.setApplicationLocales`）：

- 语言偏好由 AppCompat 自行持久化（Android 13+ 走系统 `LocaleManager`，更低版本走 AppCompat 自己的 `SharedPreferences`），**不写入 `NarviveDataStore`**，避免双源冲突；
- 读取用 `AppCompatDelegate.getApplicationLocales()`，同步、无 IO；
- 切换后 AppCompat 会**重创建 Activity**，`NavController` 的状态由 `rememberSaveable` 恢复，因此用户会停留在当前页面；
- 声明文件：`res/xml/locales_config.xml`，并在 `AndroidManifest.xml` 的 `<application>` 上用 `android:localeConfig` 引用。这样 Android 13+ 的「系统设置 → 应用 → Narvive → 语言」也能看到这三个选项并与应用内选择保持同步。

相关代码：
- `ui/prefs/AppLanguage.kt` —— 语言枚举、当前语言判定、应用语言
- `ui/screen/settings/SettingsScreen.kt`（`LanguageScreen`）—— 语言选择器（独立页面，纵向单列）
- `ui/screen/settings/SettingsViewModel.kt` —— `setLanguage()`

> `AppCompatActivity` 要求主题继承 AppCompat 主题，见 `res/values/themes.xml`（`Theme.AppCompat.Light.NoActionBar`）。这里刻意用 `Light` 而非 `DayNight`：深色/浅色一律由 Compose 侧的 `dark_theme` 偏好控制，AppCompat 不介入明暗判定，避免窗口装饰与 Compose 界面出现色差。

### 2.1 不重建 Activity，以及由此产生的编码规则（重要，勿误改）

**现状：不重建 Activity。** 这一节记录了一次完整的方案往返，**改动前请先读完**，不要重复我们走过的弯路。

#### 为什么不用官方的「重建」行为

AppCompat 默认会在语言变化时**销毁并重建 Activity**。这会暴露一帧系统绘制的空窗口，底色与当前主题相反 —— 浅色主题闪黑、深色主题闪白。**这一帧无法用应用代码遮盖**：`windowBackground`、淡入过渡都只能影响重建**之后**的帧。实测确认：加 alpha 淡入反而更糟（界面从全透明开始，用户多看到一次纯底色）。

因此本项目拦截重建。在 `AndroidManifest.xml` 的 `MainActivity` 上声明：

```xml
android:configChanges="locale|layoutDirection"
```

并在 `MainActivity.onConfigurationChanged` 里用「新 config + 已保存的 per-app locale」构造配置交给 `super`。系统于是把语言变更当普通配置变更回调，**窗口不销毁、Activity 不重建、没有闪烁**。

`attachBaseContext` 用已持久化的 per-app locale 覆盖 base context，保证任何一次创建（进程冷启动、系统回收后恢复）的首帧就是正确语言。

#### 代价：ViewModel 会跨越语言变化存活

拦截重建的**唯一代价**是：ViewModel 不再被销毁，因此**凡是把本地化文案解析成 `String` 并缓存在状态里的地方，都会停留在旧语言**。这是静默失效 —— 没有报错，只有用户看到混语言。

我们一度改回官方重建来回避这个代价，但那样换来的是一帧**用户每次都能看到**的闪烁，而闪烁出现在切换语言的设置页上。最终取舍：**接受这套编码规则，换取无闪烁**。

#### 由此产生的编码规则（新增页面必须遵守）

| 场景 | 必须用什么 |
| --- | --- |
| 纯标签（「今日」「第 N 章」） | `@StringRes Int` |
| 带参数的文案、错误消息、需要与「不可翻译的动态文本」共存 | `UiMessage`（`Res` = 资源 id + 参数；`Raw` = 数据 / 服务端原文 / AI 输出） |
| Composable 内直接渲染 | `stringResource(R.string.…)` |

**判断标准只有一条**：这个值**会不会跨越一次语言变化而继续显示**？

- **会** → 用 `@StringRes` / `UiMessage`（渲染时才解析，永远不会陈旧）
- **不会**（例如「按下按钮那一刻弹出、点掉即走」的瞬时提示）→ 可以用 `String`，陈旧窗口只有几秒

#### 光有 `UiMessage` 还不够：值也需要「重算」

这是**踩过坑才补上的一环**，务必理解两者分工：

| 机制 | 解决什么 | 不解决什么 |
| --- | --- | --- |
| `UiMessage` / `@StringRes` | 「**渲染时**按当前语言解析」 | 值本身**不会被重新计算** |
| `observeLanguageChanges { … }` | 语言变化时**重新计算值** | —— |

举例：主 AI 页的问候语是「从语言池里**随机取一句**」。就算把它包成 `UiMessage`，只要没人重新取，它就还是上次那句**旧语言的**文本。所以：

```kotlin
// ViewModel 的 init 里
observeLanguageChanges(localeProvider) {
    refreshGreeting(_uiState.value.books, profileStore.state.value.profile)  // 重算
}
```

`observeLanguageChanges` 定义在 `service/ai/PromptDefaultsI18n.kt`（连同 `PromptLocaleProvider.currentFlow()`），内部监听 `Application` 的配置变化并 `distinctUntilChanged`。**每处只需一行**，无需在界面里写刷新钩子。

**哪些地方需要它**（即「值要重算」，不是「渲染时解析」就够）：

- 从**候选池随机/挑选**的内容 —— 问候语、建议卡
- 由**多条数据聚合/映射**出来的展示对象 —— 角色会话列表项
- **依赖当前语言的兜底分支** —— 「未开始阅读」「第 N 章」「未知书籍」

  但如果这个兜底是**唯一**依赖语言的东西，更稳妥、也更省事的做法是：**把数据字段留成 `null`，兜底文案交给 Composable 在渲染时取 `stringResource`**。这样连重算都不需要。笔记列表就是这么改的 —— `NoteItem.bookTitle` / `BookChip.title` 可空，`null` 由界面渲染成「未知书籍」，见 `NotesViewModel`。

  **反例**：在 ViewModel 里写成 `bookMap[id]?.title ?: context.getString(R.string.notes_unknown_book)` —— 字符串在**构建状态时**就被定死并进了 `StateFlow`，切语言不重建 Activity 时它会一直停在旧语言。凡是 `getString` 的结果要进 `StateFlow` / `UiState` 的，都要停下来想一遍。

  例外：字符串**不进状态**、只是用户主动触发动作的即时产物（如导出 Markdown 的内容），在 ViewModel 里按需 `getString` 是允许的。

**哪些地方不需要**：字段本身就是 `@StringRes` / `UiMessage.Res` 且由数据流驱动的（如统计图表标题），数据流重新发射时自然带上新语言。

**已按此迁移的位置**：`StatsViewModel.chartLabel` 与 `FinishedBook.dateLabel`、`GlobalChatViewModel` 的 `greeting` / `suggestions` / `useEmoji`、`RoleplayViewModel.chapterLabel` / `knowledgeLabel`、`CharacterCardViewModel.chapterLabel`、`RoleplaySessionsViewModel` 的会话预览、`ReaderViewModel.fatalError`、`RewriteViewModel.error`、`FontSettingsViewModel.error`、`NotesViewModel` 的书名兜底（可空字段 + 渲染时解析）。

**已接入 `observeLanguageChanges` 的位置**（需要「重算」的那几处）：`GlobalChatViewModel`（问候语 + 建议卡）、`RoleplayViewModel`（章节标签）、`CharacterCardViewModel`（章节标签）、`RoleplaySessionsViewModel`（会话预览）。

**明确允许保留 `String` 的位置**：`ChatViewModel.error`、`GlobalChatViewModel.error`、`RoleplayViewModel.error`、`CharacterCardViewModel.error`、以及 `LibraryViewModel` 的导入错误 —— 这些都是「弹窗点掉即走」或 3 秒 Snackbar，陈旧窗口极短。**新代码不要拿它们当先例。**

#### 实现要点（踩过的坑）

- `UiMessage.text()` 是 `@Composable`，**不能**放进 `remember { }` 的 lambda 里。先在 composable 作用域解析成 `String` 再交给 `remember`（见 `GlobalChatScreen.SuggestionCard`）。
- 需要回写数据库或交给 AI 的**纯文本**（如会话的 `lastReadChapterTitle`、角色卡的 `knowledgeBoundary`），用 `UiMessage.resolve(appContext)` 在**写库那一刻**按当前语言解析一次。
- 「渲染时才追加」的装饰（如 emoji 后缀）改由界面按状态里的**偏好布尔值**追加（见 `GlobalChatUiState.useEmoji`），不要再在 ViewModel 里拼进文案。
- 建议提示词（如「总结《书名》」）**不要**预先拼好放进 action，改为**点击时**由界面按当前语言生成。

#### 什么时候会回归

去掉 `configChanges` 里的 `locale`、或去掉 `onConfigurationChanged` 覆盖，闪烁就会立刻回来。

#### 一个常见误解

**声明 `configChanges="locale"` 不会影响 Android 13+ 的系统「应用语言」联动。** 那个入口由 `res/xml/locales_config.xml`（经 `android:localeConfig` 引用）提供，与 AppCompat 是否重创建 Activity 无关；系统设置里选语言仍会写入 per-app locale，应用侧由 `onConfigurationChanged` 接住。

#### 保留的两道兜底

窗口背景与主题对齐（`res/values/themes.xml` + `res/values-night/colors.xml` + `NarviveTheme` 运行时改写）依然保留，用于覆盖**冷启动首帧**；它不再是主要手段，但去掉后冷启动会闪。

## 3. 资源文件组织

### 3.1 按模块拆分，而非单一巨型 strings.xml

每门语言下按模块拆成多个文件（aapt2 会把同一目录下的所有文件合并，文件名不影响查找）：

```
res/values/                          res/values-en/                    res/values-b+zh+Hant/
├── strings.xml              公共 + 设置            同名                    同名
├── strings_library.xml      书架 / 详情
├── strings_library_vm.xml   Library/BookDetails ViewModel 层
├── strings_reader.xml       阅读器
├── strings_viewer.xml       阅读正文 Viewer（EPUB/TXT/PDF）
├── strings_notes_stats.xml  笔记 / 统计
├── strings_stats_vm.xml     StatsViewModel 层
├── strings_chat.xml         AI 对话 UI
├── strings_chat_vm.xml      ChatViewModel 层
├── strings_ai_internal.xml  AI 内部提示词与模型交互文案
├── strings_prompt_meta.xml  PROMPT 设置页的模板标题与描述
├── strings_fonts.xml        字体设置页
└── strings_vm_messages.xml  Reader/Roleplay ViewModel 层
```

**约定**：文件名与键前缀保持一致（如 `strings_reader.xml` 里的键统一 `reader_` 前缀）。这样既避免跨模块键名冲突，也让 grep 能快速定位归属。

### 3.2 键命名

`<模块>_<语义>`，全小写 + 下划线。带参数的键用位置占位符：

```xml
<string name="library_selected_count">已选 %1$d 本</string>
<string name="reader_rest_reminder_body">已连续阅读 %1$d 分钟，起来休息一下吧。</string>
```

调用：`stringResource(R.string.library_selected_count, count)`

**严禁把一句话拆成多段拼接**——英文语序与中文不同，必须让每种语言自行决定整句的排列：

```kotlin
// ✗ 错误：英文语序无法正确表达
Text(stringResource(R.string.prefix) + count + stringResource(R.string.suffix))

// ✓ 正确：整句一个资源，占位符由翻译方排布
Text(stringResource(R.string.selected_count, count))
```

### 3.3 XML 转义（易踩坑）

英文文案里出现撇号必须转义，否则 **aapt2 直接编译失败**（`unescaped apostrophe`）：

```xml
<string name="x">the app\'s settings</string>
```

同样需要转义的：`&` → `&amp;`、`<` → `&lt;`；中文引号 `「」` 与英文弯引号 `“”` 无需转义。

## 4. 代码层的三条铁律

### 4.1 `stringResource` 只能在 `@Composable` 作用域调用

这是本项目最容易引入编译错误的地方。以下位置**禁止**调用：

- `LaunchedEffect { }`、`remember { }`、`derivedStateOf { }` 等 lambda 内部
- `onClick = { }`、`onCheckedChange = { }` 等事件回调内部（它们是普通 lambda，不是 composable）
- ViewModel、Service、Repository（根本不是 Composable）

正确做法：

```kotlin
// ✓ 在 composable 作用域先解析，再交给 effect/回调
val messageText = message?.text()
LaunchedEffect(messageText) {
    if (messageText != null) { snackbarHostState.showSnackbar(messageText); viewModel.clearMessage() }
}
```

非 Composable 场景用 `context.getString(R.string.x, args)`。

### 4.2 需要本地化文本的私有辅助函数要标 `@Composable`

如 `formatSize(Long)`、`relativeTime(Long)`、`typeLabel(...)`。把它们改成 `@Composable` 是允许且必要的改动；前提是**所有调用点都在 composable 作用域内**。

### 4.3 判定逻辑绝不能依赖文案内容

```kotlin
// ✗ 错误：英文文案里没有「成功」，颜色判定必然失效
color = if (message.contains("成功")) primary else error

// ✓ 正确：用结构化状态
data class TestResult(val ok: Boolean, val message: String)
color = if (result.ok) primary else error
```

## 5. ViewModel / Service 层的文案

ViewModel 与 Service 无法调用 `stringResource`。本项目提供两种手段：

### 5.1 `UiMessage`（`ui/message/UiMessage.kt`）—— 跨层传递可翻译消息

```kotlin
sealed interface UiMessage {
    data class Res(@StringRes val id: Int, val args: List<Any> = emptyList()) : UiMessage
    data class Raw(val text: String) : UiMessage   // 服务端 error.message / AI 输出等动态内容
}
```

- Composable 内：`message.text()`
- 非 Composable：`message.resolve(context)`

`Res` 只携带 id + 参数，**渲染时才按当前语言解析**，因此切换语言后历史消息也会跟随，不会出现中英混杂。能用 `Res` 就不要用 `Raw`。

### 5.2 `context.getString(...)`

适合 ViewModel 中进入 `UiState` 的即时提示（图表错误、连接测试结果等）。已注入 `@ApplicationContext Context` 的 ViewModel 可直接使用。

**注意其局限**：`getString` 在赋值那一刻就把语言固化成 `String`。若该文案会长期停留在界面上且在语言切换后仍可见，应改用 `UiMessage.Res` 或 `@StringRes Int` 字段。

### 5.3 枚举 / 数据类字段

字段类型用 `@StringRes Int` 而非 `String`，由 UI 侧解析：

```kotlin
enum class QuickCommand(@StringRes val labelRes: Int) { EXPLAIN(R.string.chat_vm_cmd_explain), ... }
data class AppearanceThemeSpec(val id: String, @StringRes val displayNameRes: Int, ...)
```

## 6. AI 输出语言（重要，且与普通 UI 文案不同）

AI 用什么语言回答，**不由界面框架决定，而由提示词决定**。本项目三处协同：

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 系统提示词 | `service/ai/AiText.globalSystemPrompt(lang)` | 全局 AI 主页的系统提示，决定回答语言 |
| 默认模板 | `service/ai/PromptDefaultsI18n.kt` | 12 套用户可见/可编辑模板的英文与繁体默认值 |
| 周边文案与意图路由 | `service/ai/AiText.kt` | 问候语、建议卡、注入模型的本地数据说明、**意图路由正则** |

### 6.1 硬约束：用户自定义的提示词永不被语言切换覆盖

`PromptService.get()` 的优先级是 **用户自定义值 > 当前语言默认模板**。用户在 PROMPT 设置里改过的内容属于用户数据，切换界面语言不得改写它。

### 6.2 意图路由正则必须保留中文分支

`AiText.intentStats/intentRecommend/intentProgress` 在英文界面下是**中英并集**匹配。中文用户可能用中文提问，因此**只允许新增分支，禁止删除中文关键词**——删掉会导致中文用户的功能静默失效。

### 6.3 提示词变量也要跟随语言

`scope`（全书/本章）、`author` 等变量会直接进入提示词正文，必须按当前语言取值（`AiText.scopeWholeBook/scopeThisChapter/unknownAuthor`），否则英文界面下会往提示词里插入中文。

### 6.4 JSON 输出的模板只翻译说明文字

角色卡 / 人物关系图 / 时间轴三套模板要求模型输出 JSON，其**键名与结构必须保持不变**（解析器按固定英文键读取），只能翻译说明性文字与取值示例。

## 7. 字体

界面字体为 HarmonyOS Sans，打包两套字族：

| 字族 | 文件 | 用途 |
| --- | --- | --- |
| `NarviveSansSC` | `res/font/harmonyos_sans_sc_{regular,medium,bold}.ttf` | 简体中文界面；英文界面也用这套（拉丁字形足够） |
| `NarviveSansTC` | `res/font/harmonyos_sans_tc_{regular,medium,bold}.ttf` | 繁體中文界面 |

按语言选择由 `ui/theme/Type.kt` 的 `narviveTypography(traditionalChinese)` 完成，在 `NarviveTheme` 中通过 `MaterialTheme.typography` 下发——**消费方零改动**。

为什么不共用 SC：SC 子集只覆盖简体字形，用 SC 渲染繁体用词会出现字形风格混杂（如「骨」「迴」「體」的写法差异）。两套合计约 36 MB。

> 阅读正文（EPUB/TXT/PDF）**不走**此字族，沿用 `service/font` 的独立字体系统，由用户在字体设置中自选。两者互不影响。

字体授权见 `res/raw/harmonyos_sans_license.txt`。

## 8. 新增一门语言的操作步骤

以新增日文（`ja`）为例：

1. **复制资源目录**：`res/values-en/` → `res/values-ja/`，翻译其中所有文件（保持键名与顺序不变）。
   - 只需翻译 `<string>` 内容，**不要改动 `name` 属性与占位符**（`%1$s`、`%2$d` 必须保留且序号一致）。
2. **更新 `res/xml/locales_config.xml`**：加入 `<locale android:name="ja" />`。
3. **扩展 `AppLang`**（`core/AppLang.kt`）：加入 `JA`。
4. **扩展各语言判定与文案表**：
   - `ui/prefs/AppLanguage.kt`：加入枚举项、`current()` 的判定分支、`R.string.settings_language_ja` 标签
   - `service/ai/PromptDefaultsI18n.kt` 中的 `PromptLocaleProvider.current()`：加入 `"ja"` 分支
   - `service/ai/PromptDefaultsI18n.kt`：加入 `ja` 模板表（缺失的键会自动回退简中默认值）
   - `service/ai/AiText.kt`：加入 `JA` 分支（问候语、建议卡、意图路由正则、注入说明）
   - `service/ai/AiText.kt` 与 `AiText.titlePrompt/titleLimit`：确认标题生成策略（字/词截断）
   - `ui/theme/Type.kt`：如需要专用字族则加入；否则复用 `NarviveSansSC`
   - `SettingsViewModel`：语言选择器由 `AppLanguage.entries` 自动枚举，无需改动
5. **补齐 `stats_vm_*` 日期格式**：`strings_stats_vm.xml` 的 `stats_vm_date_month_day` 是 `SimpleDateFormat` **模式串**，若目标语言日期写法不同（如「2026年8月19日」），在该语言文件里替换模式。
6. **验证**：见下节。
